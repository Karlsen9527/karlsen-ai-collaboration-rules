# 项目目录与版本管理规范

规范标识：`project-structure-and-versioning`  
规范版本：`1.0.0`  
制定日期：2026 年 10 月 7 日  
维护方：谢多多  
正文位置：`karlsen-ai-collaboration-rules/standards/PROJECT_STRUCTURE.md`  
生效依据：独立发布清单与可核对的可信用户批准

## 一 目的与适用边界

本规范统一项目的仓库边界、目录组织、版本标识和规范引用方式，适用于单文件脚本、影刀配套脚本、Agent Skill、前后端应用，以及规范文档项目。

本规范采用以下组织原则：

1. 一个独立产品或工具默认使用一个仓库。同一产品的前后端默认放在同一仓库。
2. 本规范放在现有 `karlsen-ai-collaboration-rules` 仓库的独立文件中，由谢多多维护，不混入现有通用规范 core 正文。
3. 共同要求保持轻量，各类型项目使用适合自身的结构。没有内容的目录不提前创建。

本规范的实际批准、发布和生效状态，以独立 manifest 所绑定的精确正文及可核对的可信用户批准为准。文件存在、标注 `1.0.0` 或作为候选提供审阅，均不构成生效或实施许可。规范版本、产品 release 和任务协议 schema 分别管理；认可组织原则不替代对精确发布材料和具体实施动作的批准。

本规范范围不包括调度器实现、任务签发与验签实现、安装程序、创建仓库、初始化 Git、上传业务源码、修改业务入口、自动合并或部署。R5 方案仍需独立批准；本规范仅保留它将来接入时所需的目录兼容性。

文中的“必须”表示项目正式采用本规范后应满足的要求；“建议”表示默认做法；“可选”按实际需要启用。历史项目按第十二节逐步接入，不因本规范出现而自动迁移。

## 二 仓库粒度与名称

### 2.1 一个交付单元一个仓库

默认以可独立交付、维护和验收的产品或工具作为仓库边界。

- 一个图片处理工具可以是一个仓库，即使它目前只有一个脚本。
- 一个网站产品的前端、后端及共享接口说明默认同仓。
- 一个独立发布的 skill 可以是一个仓库。
- 通用规范作为规范产品，由现有规范仓库维护。
- 临时试验文件不必立即升级为独立仓库，应先明确是否需要长期维护和交付。

只有出现明确的独立发布周期、权限隔离、独立维护责任或跨产品复用需求时，才提出拆仓方案。拆仓需说明依赖和版本如何关联，不能仅因出现两个目录就自动拆仓。

### 2.2 新仓库命名

新仓库默认采用私有可见性和 `karlsen-` 前缀，使用小写英文、数字及连字符，名称表达产品或工具用途。创建仓库和设置可见性须属于实际获准的实施范围。

新项目本地目录默认与仓库名称一致。现有目录允许保留历史名称，不为统一命名擅自重命名。

以下为 2026 年 10 月 7 日记录的接入基线，不代表此后状态始终不变：

| 项目 | 本地历史目录名 | 基线时拟远端仓库名 | 基线状态与接入边界 |
| --- | --- | --- | --- |
| 批量图片缩放工具 | `print-batch-image-resizer` | `karlsen-batch-image-resizer` | 保留原目录；远端仓库尚未创建；不自动初始化或导入源码 |

GitHub 仓库名、产品名、Python 包名和 skill 的 `name` 是不同标识。可以统一，但不能因仓库改名而自动改动代码导入名、包名或 skill 调用名。

## 三 本地工作区与路径

### 3.1 工作区根目录

本规范制定时登记的用户本地工作区根目录为 `E:\collab-workspace`。它是多个项目的容器目录，不作为所有项目共用的 Git 仓库，不在该根目录统一执行 `git init`。

本规范中的通用路径使用 `<workspace_root>`。共享任务、配置示例和结果报告使用项目标识与仓库相对路径。机器实际根目录及其他绝对路径由本地配置完成映射，不复制到任务协议或可复用配置中。前述 Windows 路径仅记录 2026 年 10 月 7 日的用户环境基线，不要求其他机器具备相同盘符。

示意：

```text
<workspace_root>/
  karlsen-example-tool/
  karlsen-example-web/
  print-batch-image-resizer/   # 保留的历史目录
```

这只是位置示意，不要求创建上述示例项目，也不要求在用户电脑建立通用规范的另一份维护副本。

### 3.2 单一维护来源

同一项目必须能确定哪一份源文件是维护源。备份、安装副本、构建输出和工作树不能各自演化成未登记的第二套产品。

通用规范在谢多多这里维护并发布。业务项目引用正式规范的固定版本，不复制 core 正文后另行修改。本地必要的只读缓存可以存在，但必须有来源和版本，不具备独立修改、发布权限。

### 3.3 将来启用并行工作时

截至本规范制定日期，R5 仍为待批准实施的独立方案；该方案的首期按同项目串行执行，本节不启用并行。

将来获准采用分支和 Git worktree 时：

- 一项并行改动使用明确的任务分支及对应工作树，记录任务、分支、工作树和基线的对应关系。
- 工作树放在同一工作区根目录下的兄弟目录，避免嵌套进另一个工作树。
- 不让两个执行器同时修改同一工作目录。
- 对共享输出、外部文件、数据库和部署目标另行处理冲突；工作树本身不提供这些资源的隔离。
- 删除工作树或分支前先检查未提交内容及保留要求，并按实际授权执行。

示意：`karlsen-example-tool/` 与 `karlsen-example-tool--TASK-001/` 为兄弟目录。Git worktree 管理的是同一仓库的多个工作树，不应当作互不相关的新仓库。[5]

## 四 所有正式接入项目的最低要求

### 4.1 根目录文件

正式采用本规范的项目，最低保留：

| 文件 | 必须说明的内容 |
| --- | --- |
| `README.md` | 项目用途、实际入口、支持环境、运行方法、验证方法，以及重要输入输出 |
| `AGENTS.md` | 适用规范的固定引用、本项目独有约束、允许修改范围、应执行的检查及必须保持的入口 |
| `.gitignore` | 按项目实际情况排除本地配置、运行状态、依赖安装目录、缓存、秘密和不应共享的数据 |

没有合适忽略项时，`.gitignore` 可以只含说明，不照搬巨型模板。最低文件应包含真实项目内容，不能用空壳文件表示已经完成接入。

README 面向项目使用者和维护者；AGENTS 面向执行任务的代理。两者可以互相链接，避免同一要求在多处分别维护。

字段按项目类型解释。纯规范项目可用阅读入口、适用范围及文档校验方法代替程序启动方式；纯指令 skill 可说明触发方式和产物验收。确实没有运行入口、依赖或业务输入输出时，明确写“不适用”及原因，不编造命令、测试或目录。

### 4.2 项目规格说明

通过代理任务派发、自动协作调度或 R5 链路接受工作的项目，必须具备 `docs/PROJECT_SPEC.md`。普通脚本内部的批处理、循环或定时能力本身不触发此要求。它至少说明：

- 项目边界、现有入口、主要模块与输入输出；
- 运行环境、依赖、启动和验证方法；
- 不得擅改的接口及约束；
- 需要保留的历史目录、特殊布局和其他例外；
- 业务源码与任务、报告仓库的关系；
- 当前可复现的源码基线表示方法；
- 项目版本的唯一声明位置；
- 本地配置与共享配置的边界。

PROJECT_SPEC 必须与真实文件一致。不适用的字段按 4.1 节说明；无代码的规范项目可以登记文档基线，无程序代码的 skill 可以登记技能包基线。任务应引用 PROJECT_SPEC 可取回的精确快照：已经入 Git 时记录仓库、commit 和相对路径；尚未入 Git 时记录获准的可取回快照及内容哈希。只有哈希而没有正文或可访问快照不足以支持复核，可变的“最新版文档”也不能作为不可变任务的唯一依据。

仅供人工使用的简单脚本，可把这些必要说明合并进 README，暂不创建 docs。启用自动协作前再补齐规定的 PROJECT_SPEC。

### 4.3 按需增加内容

以下内容按实际需要增加：`docs/`、`tests/`、`examples/`、`scripts/`、`assets/`、CI 配置、变更记录、包配置和项目清单。

- 不强制所有项目拥有 `src/`。
- 不要求为凑齐模板创建空目录。
- 没有测试目录不等于无需验证。README 或 PROJECT_SPEC 必须说明当前实际检查方法和未覆盖部分。
- 已有框架约定、语言工具链或发布平台的要求优先保留，通过项目说明登记结构。

## 五 各类项目的目录规则

以下均为示例，不是待自动执行的目录创建命令。示例中的可选目录只在包含实际内容时创建。

### 5.1 单文件脚本与影刀配套脚本

单文件脚本可以直接放在项目根目录。不要为增加 `src/` 而移动入口或改写导入路径。

```text
karlsen-example-script/
  README.md
  AGENTS.md
  .gitignore
  existing_entry.py
```

`existing_entry.py` 表示现有真实入口，不要求将任何脚本改成这个名字。

影刀相关项目必须在 AGENTS 或 PROJECT_SPEC 中记录现有四个 imports、main 入口以及调用方式。目录整理不得擅自修改这些内容，也不得假设可以改成另一种运行模式。需要调整时，由具体任务说明兼容影响、验证方法和获准范围。

依赖声明、测试脚本和样例数据仅在需要时添加；样例必须适合共享，不能用用户原始业务数据代替测试样例。

### 5.2 项目内使用的 skill

项目专用 skill 的默认发现位置为：

```text
karlsen-example-product/
  README.md
  AGENTS.md
  .gitignore
  .agents/
    skills/
      karlsen-example-skill/
        SKILL.md
        scripts/       # 可选
        references/    # 可选
        assets/        # 可选
```

skill 包必须包含 `SKILL.md`，其 frontmatter 至少包含 `name` 和 `description`。`name` 应符合 Agent Skills 标准，并与 skill 所在的直接父目录名匹配。[1]

仓库名的 `karlsen-` 前缀要求不应误用成对整个仓库结构的 skill 格式要求。上例的仓库叫 `karlsen-example-product`，skill 包目录和 name 可以叫 `karlsen-example-skill`。

Codex 在项目目录层级中查找 `.agents/skills`。仅把某个 skill 仓库放进工作区，不代表它已经进入项目发现路径。[2]

### 5.3 独立发布的 skill

一个独立发布的 skill 可将仓库根目录作为 skill 包根目录：

```text
karlsen-example-skill/
  SKILL.md
  README.md
  AGENTS.md
  .gitignore
  scripts/             # 可选
  references/          # 可选
  assets/              # 可选
```

此时 skill 包根目录名与 SKILL.md 的 name 保持一致。远端仓库名称与安装时的 skill 包目录名是不同层面的标识，应分别校验。

根目录的 SKILL.md 是发布源；安装到项目的 `.agents/skills/<skill-name>/` 是发现和使用位置。两种用途不能混为一谈。

必须选定唯一可编辑维护源。安装记录应包含来源仓库与源包相对路径、固定版本（如有）、精确来源 commit 或可取回的发布包标识、安装位置，以及实际安装包的文件范围和可验证内容哈希。校验范围覆盖实际安装和使用的 SKILL.md、scripts、references、assets 及其他随包文件；只对未安装或未使用文件作出的排除须列明，不能漏掉实际依赖，也不能只核对 SKILL.md 或版本文字就声称整个安装包一致。该记录可使用已有项目说明或安装记录，不强制另建安装器、数据库或校验脚本。

安装后实际核对来源与内容。安装副本如被修改，应标记为本地偏离，并记录差异；在重新核对前不能继续宣称与原发布版精确一致。不能在安装副本里独立维护另一套逻辑。更新先发生在维护源，再经验证更新安装版本。本规范不选择或实施具体安装方式，也不创建符号链接或同步脚本。

### 5.4 同一产品的前后端应用

新项目可采用：

```text
karlsen-example-web/
  README.md
  AGENTS.md
  .gitignore
  docs/
    PROJECT_SPEC.md
  apps/
    frontend/
    backend/
```

如确有共享代码，可增加 `packages/`；如需要部署说明，可增加 `docs/deployment/`。没有这些内容时不创建目录。

已有 `frontend/`、`backend/`、`web/`、`server/` 或框架约定结构可继续使用，并在 PROJECT_SPEC 登记路径。统一规范不指定前后端框架、包管理器或数据库，也不要求为了示例迁移目录。

同仓不强制前后端使用相同版本或同步发布。可以采用统一产品版本，也可以让前后端作为独立发布单元分别编号；沿用项目已有且清楚的政策，并在 README 或 PROJECT_SPEC 中登记各自版本来源、适用范围和兼容关系。每个发布单元只有一个权威版本来源。组件独立版本不自动构成拆仓理由；是否拆仓另按第二节决定。

### 5.5 规范与文档项目

规范项目可以以根目录文档、`core/`、`docs/`、`standards/` 和发布材料为主体，不要求存在应用入口或 src。

本规范正文位于现有规范仓库的 `standards/PROJECT_STRUCTURE.md`。发布本规范时，既有 core 文件、通用 v1.0.0 发布文件、校验记录、目录及已有标签保持原位和原内容。已有其他入口文件、通用 ZIP 与独立的 R5 方案均不因本规范发布而替换。

## 六 任务和报告目录的兼容约定

本节只描述 R5 将来启用后的目录接口，不代表本地程序、受信发布端或自动执行已经就绪。具体任务字段、审批凭证、执行状态和调度逻辑继续由单独批准的 R5 方案管理。

| 目录 | 唯一内容责任方 |
| --- | --- |
| `tasks/codex/<task_id>/<revision>/` | 谢多多的受信发布端写入 Codex 任务及批准凭证 |
| `tasks/dsh/<task_id>/<revision>/` | 谢多多的受信发布端写入 dsh 任务及批准凭证 |
| `reports/run/<task_id>/<run_id>/` | 本地程序写入领单、开始、停止、异常及交付回执 |
| `reports/codex/<task_id>/<run_id>/` | Codex 执行器产出结果与获准证据 |
| `reports/dsh/<task_id>/<run_id>/` | dsh 执行器产出结果与获准证据 |
| `reports/review/<task_id>/<run_id>/` | 谢多多写入复核结论 |

本地程序可以代上传执行器结果，但不能改写其结论。每条内容仍保留实际产出者与来源。任务批准后不覆盖原 revision；回执按序追加；已固化的结果与所引用证据保持原内容。

同一次运行的报告修正，在对应角色和原 run_id 下按序新增版本或修正记录，保留原文件并说明原因，不覆盖旧报告或证据，不因补交、修正文案而虚构新的 run_id。只有实际再次运行才使用新的 run_id，并按获准任务及 R5 的重试规则执行。代理上传只传递获准内容；不通过改写已固化文件来筛选或伪装证据。

不建立让多个角色共同改写的总状态 index、总任务表或总报告文件。需要汇总时，应从各角色记录读取生成只读视图，并明确它不具备任务授权效力。

`tasks/`、`reports/` 只在获准接入任务链路时按需创建。运行中的本地原始日志、SQLite、锁和缓存不因此进入 reports 上传范围。

## 七 版本与源码基线

### 7.1 分清版本的用途

| 标识 | 表达什么 | 不替代什么 |
| --- | --- | --- |
| 产品版本 | 对使用者交付的软件、脚本或 skill 版本 | 不替代任务 revision 或具体源码基线 |
| 规范版本 | 所采用规则及其兼容性承诺 | 不因产品发版而自动变化 |
| schema_version | 机器读取格式的结构兼容性 | 不等于文档标题版本；没有机器格式时不额外创建 |
| task_id 与 revision | 一个任务及其精确要求的修订 | 不等于产品发布或协议版本 |
| run_id | 某任务版本的一次运行 | 不代表新的任务授权 |
| Git commit | 一个仓库的精确文件状态 | 不自动证明它包含被执行的业务源码 |
| 文件或快照哈希 | 精确内容的完整性 | 不证明授权、发布、回滚能力或 Git 历史 |

`R5` 是现有方案的修订标识，不能直接当作所有产品版本或未来已生效的 schema 版本。

### 7.2 每个发布单元的唯一版本来源

一个仓库可以包含多个发布单元。产品、独立组件、skill 和规范各自按已登记的政策编号，不要求它们版本相同，也不因其中一个发布而自动升级其余版本。

有现成包元数据的发布单元，优先使用工具链已有的权威版本来源，例如项目实际采用的 package.json、pyproject.toml 字段或既有动态版本来源。先确认哪个值是权威来源，不能把自动生成的显示值误当成另一套手工来源。其他地方需要显示版本时，应引用或从这个来源生成，避免手工维护多个不同数值。

没有适用包元数据、但确需正式发布的项目，包括简单脚本和独立 skill，可在 README 或 PROJECT_SPEC 中登记唯一版本来源。例如采用根目录 `project.json` 的 version 字段，或保留项目已有的唯一版本文件；引入新文件前先确定实际读取方和最小内容。不能同时新增 project.json、VERSION 和脚本内常量，要求人工同步三处，也不为声明版本强制简单项目新增 docs。

尚无正式发布需求的脚本，可先用精确源码基线标识，不为了填表伪造 release。

### 7.3 有兼容契约时使用语义化版本

采用 `MAJOR.MINOR.PATCH` 前，先写清兼容契约。对脚本可包括入口、参数、输入输出格式；对服务可包括接口和配置；对 skill 可包括调用方式、输入要求及产物约定。契约面向其使用者，并不意味着仓库必须公开。

一般政策：

- MAJOR：对已承诺的契约作不兼容变更。
- MINOR：增加向后兼容的能力。
- PATCH：向后兼容的修复，不改变已承诺用法。

早期 `0.x.y` 表示初始开发阶段，不能让使用者误以为已具备稳定的 1.0 兼容承诺。即使处于早期阶段，仍须说明破坏性变化，不把版本号当作免说明理由。[3]

草案审阅编号如历史 `v0.1`、`v0.2`，应与规范的正式三段式版本分别标注。尚未建立兼容契约时，可以使用明确的修订号或提交，不虚称符合完整 SemVer。

### 7.4 规范版本的语义

正式发布本规范时，建议把已定义的目录和引用约定视为兼容契约：

- PATCH：纠错、澄清或示例修正，不改变原有必须遵守的义务。
- MINOR：新增向后兼容的可选能力，原合规项目仍可继续合规。
- MAJOR：删除或更改已有约定，或新增会使原合规项目必须修改才能继续合规的强制要求。

不能仅因为“只是文档”就把新增强制要求当作 PATCH。草案期间可迭代审阅编号，但不得覆盖已经批准的精确材料来沿用旧批准。

### 7.5 精确源码基线

任务、交付和复核记录合起来必须区分：任务所在仓库与提交、报告所在仓库与提交、实际业务源码基线。结果正文可以记录任务提交与源码基线；报告自身所在的最终提交由交付链接或后续复核记录引用，不要求报告在同一文件中预先写入包含自身的 commit，避免自引用循环。

- 业务源码已纳入 Git：记录源码仓库、精确 commit，以及与运行相关的未提交修改和未跟踪文件。存在这些额外输入时，需在获准范围内补充差异或快照；不能只给 commit 就声称完整定位了执行输入。
- 业务源码尚未纳入 Git：可在获准范围内记录选定源文件的相对路径、大小和内容哈希，以及可复核的源快照说明。排除秘密和不在范围内的文件，不借记录快照上传原始业务数据。
- 初期仓库如果只存 TASK、RESULT 和报告，其 commit 只能定位这些文件，不能充当本地业务源码的 commit。
- 快照哈希证明内容一致，不提供 Git 提交历史，也不自动提供可恢复的备份。

对保留的非 Git 历史源码，不因需要基线而自动初始化、提交或上传。

## 八 分支 提交与发布标记

日常修改通过清楚描述范围的提交记录。涉及协作时采用与任务可关联的分支和 PR；具体分支名服从项目已有约定，不为本规范强制改名。

提交、推送、建立 PR、合并和产品发布分别属于不同动作。写入“测试通过”或将 PR 设为 ready，不会自动批准后续动作。

发布需要做到：

1. 明确发布版本与来源 commit。
2. 保留实际验证结果、已知限制及兼容变化。
3. 发布标签确定后不强制移动、覆盖或删除后重建来掩盖变化。
4. 已发布内容发生变化时使用新的版本，保留旧版可追溯性。
5. 标签名可带 `v` 前缀；正式版本值与标签名的表示方式在项目中固定。[3]

分支头会变化，不用 `main` 或“最新代码”代替要求可复现的精确版本。远端推送成功、检查通过、发布完成必须分别核实，不合并成未经验证的完成结论。

## 九 通用规范引用与本规范发布

### 9.1 使用固定引用

项目的 AGENTS 或 PROJECT_SPEC 至少记录：

- 规范来源仓库；
- 采用的文件路径；
- 各份规范自己的正式版本；若已发布标签，记录其独立标签名；
- 可取回该版正文的精确 commit 和仓库相对路径，以及用于校验的文件哈希；
- 适用范围及经批准的项目例外。

同一规范仓库可以包含多份独立版本的标准。每份标准分别登记标识、版本、路径和固定 commit；不能只写仓库的一个笼统版本号来代表所有文件。版本号或哈希帮助识别与校验，但单独一个哈希不能取回旧正文。保留的不可变标签应能解析到相应 commit，并验证该提交下的指定路径与文件哈希一致。

既有规范没有发布标签时，以精确 commit、相对路径和文件哈希定位，不为采用本规范补造历史标签。第 9.2 节的独立标签政策适用于本目录标准今后的发布，不倒推为对既有通用 v1.0.0 的改造要求。

分别核验所采用标准的标识、版本、正文哈希和发布状态。同仓其他文件或其他标准发生变化，不自动表示本标准出现了新版本。

本规范制定时采用已发布的 `karlsen-ai-collaboration-rules v1.0.0` 作为既有通用规范基线。本目录规范独立发布，不能把它写成已包含于该通用 v1.0.0。独立发布完成前，其外置发布记录标明尚未生效；发布完成后的状态也由该记录与真实批准确定，不通过改写正文状态来沿用旧哈希。实际 tag、commit 和哈希从可信发布材料中核对，不填造示例值。

升级引用时审查差异与项目影响，再更新声明；不自动跟随 main、latest 或远端最新标签。项目只保留必要引用和自己的补充约束，不复制通用 core 正文另行维护。

固定版本不取消既有通用规则 R019 的要求：正式处理前仍检查可信来源的发布状态。检查是否有更新与自动采用更新是两件事。发现变化后评估适用范围、兼容性和影响，并取得所需批准后才调整采用版本；确认正文未变时，可以复用已核实的缓存，不必反复读取同一正文。

### 9.2 独立发布记录

本规范使用以下独立发布清单目录：

```text
standards/
  PROJECT_STRUCTURE.md
  releases/
    project-structure/
      <正式版本>/
        manifest.json
```

文中指定路径不表示文件已经提交或发布。实施发布前先核实仓库现状，避免与既有目录冲突；不得移动或覆盖通用 v1.0.0 的发布目录和清单。

独立清单至少记录标准标识、正式版本、独立发布标签名、文档相对路径、文档哈希、批准所对应的精确审阅材料、批准来源引用、批准时间，以及所引用的既有通用规范版本。标准版本与正文一致，清单只绑定发布材料，不另造一套正文版本。需要的新增字段应先定义，不得伪造实际批准记录。

本标准的标签采用独立命名空间，例如 `project-structure-v<正式版本>`，避免与通用规范的 `v1.0.0` 混淆。标签名可在候选发布材料中先确定；标签在包含最终正文和清单的提交形成后指向该提交，不要求清单包含自身所在的 commit SHA。发布后核对并记录“标准版本、标签、固定 commit、正文相对路径、正文哈希”的对应关系。

每个旧版本的清单和发布标签均须保留。`standards/PROJECT_STRUCTURE.md` 在新提交中演进时，旧版仍通过旧标签对应的固定 commit 读取原正文，不能使用当前分支的同名文件冒充旧版。这个历史定位使用 Git 已有能力，不新增平行维护副本。

发布顺序为：先准备包含正式版本号及最终状态文案的候选正文，再计算该正文的哈希，将完整候选正文、哈希及发布范围交给用户确认。用户确认后，只补充或更新独立 manifest 中的批准记录，不能再把正文中的“草案”“待批准”等字样改成另一套状态文案而继续沿用旧哈希或旧批准。若正文确需调整，应形成新的精确候选版本并重新确认。进入批准环节的正文必须已使用可在发布后继续保持不变的版本和状态表述；候选是否待批、是否已发布等可变状态放在外置清单中，不写成批准后还要修改的正文断言。

发布过程还必须保持：

- 用户确认的是一份精确正文及明确发布范围。
- 批准后正文再改，需重新确认改动，不能沿用原正文批准。
- 文档哈希计算范围清楚，发布清单自身不包含在它所声明的正文哈希中。
- 不要求一个文件同时包含自身的最终哈希，也不把即将生成的 commit SHA 写进同一提交中的文件形成循环。
- 发布后可通过不可变标签或另行记录确定实际来源 commit。
- 清单中自填的 approved、审批引用或哈希不构成独立授权；实际批准必须能够核对。
- 不改动既有 core 正文、v1.0.0 已发布内容及其哈希；新增独立标准不应伪装成对旧 release 的覆盖。

本节只规定可审查的发布记录，不扩展为签名系统或调度器实现项目。

## 十 本地数据与共享内容

默认不进入仓库或报告上传的内容包括：

- 密码、令牌、密钥、登录状态和带凭据的配置；
- 本地 SQLite、任务运行账本、锁文件、心跳和临时状态；
- 未筛选的原始日志、崩溃转储及可能含秘密的诊断包；
- 依赖安装目录、缓存、临时构建输出；
- 用户原始图片、未获准共享的业务素材，以及本地输入输出大文件；
- 包含机器绝对路径或个人环境值的本地配置。

公开可用、获准使用的少量样例和验证夹具，可以按项目需要纳入。应保留必要的依赖声明和锁文件，不能因排除依赖安装目录而把它们一并忽略。

`reports/` 只保留获准共享的精简报告和证据，不是原始日志的自动上传目录。不要用“忽略所有报告”的通用规则误排除 R5 所需的已批准报告。

`.gitignore` 是版本控制便利规则，不是权限系统、秘密扫描器或安全边界。它不阻止强制添加文件，也不会让已跟踪的文件自动退出版本控制。[4]

如果发现秘密或不应共享的数据已被跟踪，先报告现状和影响，再形成获准处理方案。新增 ignore 规则不等于问题已解决；停止跟踪、删除文件、改写历史、清理远端或更换凭据是不同动作，不能擅自一并执行。

## 十一 项目例外记录

现有项目与推荐目录不一致时，允许登记例外。例外至少说明：

- 当前实际路径或结构；
- 保留原因及依赖该结构的入口；
- 是否影响运行、验证、发布或自动协作；
- 后续调整是否必要，以及对应的具体授权。

例外可以写在 README 或 PROJECT_SPEC，不强制单建数据库或中心索引。可迁移性问题通过本地映射解决，不把机器绝对路径扩散到共享任务。

例外不能修改审批要求、扩大任务权限或把未启用的功能标为已上线。

## 十二 历史项目逐步采纳

采用本规范分为三个阶段，每个阶段都应有明确范围：

### 阶段一 盘点与声明

确认目录、入口、Git 状态、版本来源和已有约束，标明历史名称与仓库名称的映射。先找出会影响运行的真实差异，不批量移动文件。

### 阶段二 最小补齐

在获准项目中补充 README、AGENTS、必要的 ignore 规则，以及自动协作所需 PROJECT_SPEC。保留现有入口和框架布局，记录例外。新增说明不应顺带改写业务代码。

### 阶段三 有明确收益的迁移

只有迁移确有收益时，再提出逐项目计划，包括文件清单、入口影响、验证、备份和恢复条件，以及新建仓库或上传范围。用户确认后执行。

2026 年 10 月 7 日记录的 `print-batch-image-resizer` 接入基线为保留历史源码。本规范本身不授权将其初始化为 Git、迁入拟建仓库、重命名、修改影刀入口或替换旧入口文档；后续状态变化以具体获准任务及实际结果为准。
