## 从草稿到正式

1. 维护者先准备最终候选正文，包括拟正式发布的版本、状态和生效文案。此时清单仍标记为审查草稿；候选正文中的状态文案不构成有效批准。
2. 计算候选正文原始 UTF-8 字节 SHA-256，固定供审查的候选提交。哈希只计算正文，不含 manifest，避免自引用。
3. 用户在经过认证的授权渠道确认该版本、哈希对应的确切正文内容。创建仓库或推送的授权不能替代全文批准。
4. 获批后更新发布清单：status 改为 approved、effective 改为 true，并填写 approved_release 的 version、protocol_sha256 和 approval_reference。不得修改已批准的正文；任何正文改动都必须重新计算哈希并取得对应确认。批准引用采用不含秘密或个人信息的标识，对应证据留在授权渠道；仓库文字本身不证明批准。同步配套文档中的发布状态与记录，不改变已批准的正文。
5. 在待发布的同一提交中核验正文与 manifest，确认正文哈希与用户批准的候选完全一致后发布。发布提交 ID 由 Git/可信发布源提供，不写回清单造成循环。

版本号相同不代表内容相同，以正文哈希和可信批准证据共同确定。首次 approved 之前不存在可回退的已批准版本。后续撤回发布或丢失权限时，缓存不能恢复有效授权。

本版未配置 GitHub 保护规则、签名验证、自动发布或拉取服务。本次按上述约定人工办理发布；流程未自动化，各客户端接入仍需授权与实测。
