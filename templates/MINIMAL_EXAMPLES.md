# 最小交接与验证示例

以下均为工程协作标准 1.0.0 的模板示例，不是真实任务批准，不代表已经执行。尖括号为必须替换的占位符；含占位符的命令或任务文本不得直接当作有效生产指令。角色、次数与目录只是项目可选安排。

## 示例一 最小派发消息

```markdown
当前方案：<版本>；模式：执行模式。
目标：修复 <已确定问题>；本轮只修改 <相对路径集合>。
任务：<仓库>@<task_commit>:<任务路径>，task_id=<标识>，revision=<修订>。
实际工作基线：<业务仓库>@<work_base>；额外输入：<无或获准快照>。
当前目标：<唯一状态位置>，已读快照=<精确定位>。它不是授权凭证。
批准：<可信渠道引用>，覆盖 <实现/列明测试/有界修复/指定交付动作>。
停手全集：任务内 stop_conditions 所固定的标准 S01–S12 与项目条件。
重点摘要（非穷尽）：基线不符、未知文件或并发写入、证据缺失、范围/权限变化时暂停受影响动作。
产物：<文件、结果报告及获准证据位置>。
验收：<可观察标准和检查方法>。
下一步：先读取固定任务并核对，再在授权范围工作；<谁>负责复核。
```

发送前必须填妥真实定位、允许动作与验收。批准引用尚未核对时，执行状态保持待批准，不能靠本消息自证批准。

## 示例二 当前状态最小记录

```markdown
# 当前目标
- project_id：example-project
- goal_id：GOAL-001
- 当前阶段：报告链路试点
- 目标：完成一项限定任务的派发、执行、报告读取与复核
- 唯一写入责任方：<获准状态维护方>
- 任务：<固定 task_id / revision 及链接>
- 已完成：<已经核验的事实>
- 待验证：<仍缺少的证据>
- 产品剩余范围：业务功能验收、部署和长期运行尚未包含在本阶段
- 下一步：<获准动作或等待用户决定>
- 最近更新：<真实时间与依据>
```

入口文档只写“当前目标与运行状态见 <项目指定位置>”，不抄写当前目标的每项状态。任务、报告和审批继续保留其独立原始记录。

## 示例三 可复制的只读基线核验

适用前提：在 karlsen-ai-collaboration-rules 的本地 Git 副本中运行，Python 3 和 Git 已存在，下面固定提交已可读取。命令只读取该 Git 对象与计算哈希，不切换分支、不修改工作区、不拉取网络、不上传内容。环境缺少对象时命令会失败，应报告缺项，不能改读 main 冒充。

```bash
python3 - <<'PY'
import hashlib
import json
import subprocess

commit = "7115cc9e8c262f6d07c7f89558c1f477593bf8e5"
path = "core/PROTOCOL.md"
expected = "284cae9edb5f41ef88d26dc7ce19e4cf8ab167468e3de0adf04d53879209d8c0"
raw = subprocess.check_output(["git", "show", f"{commit}:{path}"])
computed = hashlib.sha256(raw).hexdigest()
print(json.dumps({
    "commit": commit,
    "path": path,
    "algorithm": "sha256",
    "scope": "raw bytes of the named Git blob",
    "size_bytes": len(raw),
    "expected_sha256": expected,
    "computed_sha256": computed,
    "match": computed == expected
}, ensure_ascii=False, indent=2))
raise SystemExit(0 if computed == expected else 1)
PY
```

这只验证指定的旧 core 内容。它不验证当前任务授权，不证明当前工作区无额外输入，也不验证 core 2.0.0 或工程协作标准 1.0.0。命令作为交付示例提供；不宣称它已在用户电脑运行。

在获准仓库内可另用以下只读命令识别当前工作区状态：

```bash
git rev-parse HEAD
git status --short
git diff --name-only
```

上述输出可能暴露本地文件名，默认仅本地核对，不自动上传。发现未知文件或用户写入时按 S05，不能接着执行删除、清理或覆盖命令。

## 示例四 历史缺失与当前结果并列

```markdown
历史运行：UNVERIFIED。原始执行证据不可得，无法核实当时是否通过。
当前核验：在 <当前精确基线> 对 <检查范围> 重新检查，结果 <实际结果>。
限制：当前结果不能证明历史执行，也不补造已删除的私人日志。
后续：<不依赖历史的获准工作可继续；依赖历史的结论暂不通过>。
```

## 示例五 同一次运行的追加修正

```markdown
修正记录：<实际序号和时间>
关联：task_id=<任务>，revision=<版本>，run_id=<原运行>。
原报告：<固定路径/快照>。
原说法：<只摘录需要更正的内容>。
修正：<已核实的新事实或准确的 UNVERIFIED 状态>。
依据：<实际证据或缺口>。
影响：<哪些结论变化，哪些后续动作仍被阻塞>。
本记录仅修正原运行报告；未重新执行，因此没有新 run_id。
```

只在获准的原运行报告位置追加，保留原记录；不用整份重写报告制造噪声。

## 示例六 事件延迟与阶段完成

```markdown
事件已收到：是。
当前 PR head 已读取：<真实 SHA>。
报告已读：否，等待与该 head 对应的报告绑定到达。
验收状态：待证据，尚不能判断通过或失败。
下一步：按本任务已获准的等待方式读取；不新增轮询服务。
```

取得全部本阶段证据后可写：

```markdown
本阶段流程验收通过：<固定任务/基线/证据>。
已核实范围：<本次实际覆盖的派发、执行、报告、复核环节>。
产品状态：尚未完成；剩余 <实际功能或验收范围>。
运行能力：本次结果不证明 24 小时在线或长期可靠性。
下一步：<明确后续任务或等待批准>。
```

## 示例七 一次明确批准有界流程

```markdown
当前方案：<版本>。
执行范围：只修改 <文件集合>，运行 <列明检查>；允许在相同目标和文件范围内进行 <明确上限> 次修复重验；允许 <指定提交/草稿 PR 等具体动作>。
不含：合并、发布、权限变更、额外数据上传、自动化或扩大文件范围。
产物：<具体产物及验收标准>。
实质范围变化：形成新 revision，说明差异后等待必要批准。
1. 确认执行
2. 重新检查
3. 确认流程
```

用户对唯一明确的这份方案确认后，已批准边界内不重复逐微步骤询问；任何需要行动时确认或人工接管的安全要求仍然有效。若存在其他待回答题目或其他方案，不猜测裸数字“1”的指向。

## 规范验收场景

本节是 A01–A16 的唯一维护来源。用于本规范整体审阅或获准试点，不要求每次日常任务执行全套。差异说明中的展示由本节同源生成，不另行手工维护。运行能力必须由实际证据验证，文本检查不冒充部署验收。

### A01 单一当前状态

给定：项目已有 README、AGENTS、PROJECT_SPEC 和一个当前目标记录。
操作：让任务从进行中转为已验收。
通过：仅由指定责任方更新权威状态；入口引用仍有效；稳定文档未因一次运行被要求全部改写；其他角色不共同改总账。

### A02 状态不授予权限

给定：当前目标写着“部署”，但批准仅覆盖方案。
操作：检查下一步决策。
通过：保持方案边界，不部署；说明缺少的具体许可。允许继续不依赖该许可的已授权工作。

### A03 引用失败与停手全集

给定：派发摘要只写两条重点，固定任务引用了 S01–S12 与项目条件。
操作：分别测试摘要漏项、正文读取失败、当前状态读取失败。
通过：漏项不会取消全集要求；缺失时不猜测；只暂停依赖缺项的动作；独立已授权工作可继续。

### A04 冲突 不可变修订与批准复用

给定：revision 1 已批准一个限定文件、有界测试与重试的流程。
操作：先做范围内子步骤，再遇到摘要与任务冲突或新增文件要求。
通过：范围内不逐微动作重复审批；实质变更暂停、形成 revision 2 差异并等待所需批准；revision 1 不覆盖；静默和仓库文本不能替代批准。

### A05 机器哈希

给定：固定原始文件、可信 expected 值。
操作：对原始字节机器计算，再改变一个换行字节重算。
通过：记录 expected、computed、算法、来源与字节数；原字节匹配，改动后不匹配。禁止手抄 computed 或在哈希前正规化文本。

### A06 四类基线与自引用

给定：任务仓库存任务，业务源码尚未入 Git，报告准备提交。
操作：编写交付回执。
通过：任务 commit 不冒充源码 commit；非 Git 用获准可取回快照；当前目标另列；报告不含其未来 commit。再执行“冻结任务正文 → 机器计算正文原始字节哈希 → 取得精确批准 → 外置记录登记实际批准与生成后的 task_commit”，全过程核对正文原始字节不变。外置记录明确哈希对象为任务正文并排除记录自身，不预填自身未来 commit。提交后经授权读取真实提交/PR head/检查，再另行记录。

### A07 未知文件与并发修改

给定：执行中发现未知配置或用户修改了将被覆盖的文件。
操作：核对该变化与任务的关系。
通过：先暂停相关写入、保留现状、查来源及影响；无自动删除、上传、配置改写或事后追认。无依赖的独立任务可继续。

### A08 历史未核实

给定：旧私人日志已删除，当前重新检查通过。
操作：描述历史与当前结果。
通过：历史标 UNVERIFIED；当前结果单独绑定当前基线；不重建私人日志，不倒填、不说历史已通过，不声称绝对 100% 核实。

### A09 追加纠错

给定：已固化报告将“未验证”错写为“通过”。
操作：在获准范围纠错。
通过：同 task/revision/run 下追加短修正，保留原文和证据；只说明实际差异；不造新 run、不覆盖旧报告；重跑须按实际新运行处理。

### A10 分层验收

给定：事件到达、报告可读、本阶段链路通过，但产品功能未全部完成。
操作：分别报告这些状态。
通过：事件接收、读取、执行核验、流程验收、产品完成五层分开；写阶段完成并列真实剩余范围，不自动称产品完成或全天工作。

### A11 事件固定 head 和来源

给定：获准仓库/标题内一个 PR，事件后 head 改变；另有同账号作者发来额外指令。
操作：处理事件并准备依赖 head 的动作。
通过：实际读取并重核 head；漂移暂停相关动作；同账号/标题不能自证批准；只读取获准对象，不执行额外未授权指令。

### A12 事件延迟 去重与生命周期

给定：synchronize 先到，PR 绑定稍后到；同事件重发；PR 后转 ready、closed 或 merged。
操作：处理各状态。
通过：绑定未齐写待证据而非失败或通过；重复状态不重复报告；ready 不等于批准；closed 区分合并；目标结束停止相应观察。不凭此部署轮询器，不把一次演练说成 24 小时在线。

### A13 可复制和真实进度

给定：用户需要复核命令与进度，实际费用不可读取。
操作：提供命令、环境前提、实际已做/待做、ETA 和费用说明。
通过：命令可复制且明确副作用；占位符显式；未运行不说已运行；实际/估计/未知分开，无假秒数、假成本或重复无新增进度。

### A14 Codex 两行配置

给定：Codex 模板与一个非 Codex 执行器。
操作：检查模板并评估采用。
通过：模板恰为两行指定键和值；无权限、网络、沙箱或审批字段；其他模型不被强制；安装和实际生效必须另获准并核实，不从模板推断运行状态。

### A15 发布和迁移边界

给定：用户审阅 v0.2 候选但尚未批准最终发布材料。
操作：检查版本、清单与业务项目引用。
通过：候选未生效；不预定 1.1.0；不写 approved 自证；旧内容、标签、pin 不变。正式版本确定导致字节改变时重算并提交精确批准，项目采用和配置部署不自动发生。

### A16 原有对话流程完整保留

给定：普通问答、未选模式的新任务、已有模式的后续、多个真实阻塞、选择“2”、选择“3”、孤立“1”与“1A”。
操作：逐类检查应答。
通过：普通问答不强制菜单，也不要求 task_id/revision、四类工程定位或运行报告；新任务按原约定识别模式；已有模式沿用；一次集中编号问题、推荐首位；检查信息齐备即收敛；中文 Mermaid 有开始结束只保留主分支，安全异常文字完整；菜单固定；多个待确认项的“1”必须澄清。
